## Prioritized findings

### A01 — High, confirmed source defect: unauthenticated Telegram updates act as the default owner

**Evidence:** initial `src/index.ts:73` exposes `POST /telegram`; initial `src/handlers/telegram.ts:27` constructs the bot/services/cache without authentication and selects `DEFAULT_USER_ID` at line 31. Lines 103–106 deserialize and process arbitrary updates. Lines 162–167 invoke owner-context AI; lines 260–283 write transactions with service credentials; lines 293–318 send an account balance and transaction details to the update's chat.

**Preconditions/impact:** a deployed, reachable Worker route and configured bot/default owner. AI processing additionally needs the owner's relevant consent and usable provider credentials. An attacker can submit a forged update, or send text to the real bot, to cause owner financial writes, AI spending and balance disclosure to an attacker-controlled chat. Webhook authenticity alone would still leave any actual Telegram user able to act as that owner. No production exploitation was attempted.

**Minimal remediation:** fail closed before body parsing/DI unless a server secret matches `X-Telegram-Bot-Api-Secret-Token`; require a bound private owner chat **and** sender; bound the body and accepted update shape. Recommended configuration: `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_OWNER_CHAT_ID`, `TELEGRAM_OWNER_USER_ID`. Missing configuration must disable intake. Configure Telegram's `secret_token` and limit accepted updates to `message`; do not reflect private errors into chat. The concurrent Telegram patch requires independent review and deployment verification.

### A02 — High, confirmed source defect: global webhook setup accepts ordinary user/API credentials

**Evidence:** initial `src/index.ts:45` authenticates `/setup-webhook` with `resolveUserId`, without an owner/admin authorization check. `src/utils/auth.ts:23` accepts any valid per-user key before its JWT branch. Initial `src/index.ts:50` derives the global webhook target from the incoming request origin, and line 51 omits `secret_token`.

**Preconditions/impact:** any valid ordinary Anotto credential can request a change to the shared Telegram bot webhook. Control over a routable alternate hostname/request origin would add a webhook-redirection risk; such a hostname was not demonstrated. The confirmed defect is missing authorization for a global administration operation.

**Minimal remediation:** require an interactive, verified Supabase JWT for the server-configured owner, and an explicitly trusted canonical Worker webhook URL. Use `POST` to Telegram with JSON containing `url`, `secret_token` and `allowed_updates: ['message']`; protect secrets from request logging. Do not use the web application's `APP_URL` as an assumed Worker address.

### A03 — High, confirmed source defect: several paid AI paths bypass reservation limits

**Evidence:** `src/handlers/parse.ts:85` reserves AI quota through `beforeExternalCall`. In contrast, initial `src/handlers/transaction.ts:87`, `src/handlers/email.ts:100`, and `src/handlers/telegram.ts:162` call the same parser without that hook. `src/parsers/expense.ts:74` requires consent but invokes reservation only optionally at line 76. `src/services/supabase/ai-usage.service.ts:43` explicitly makes telemetry best effort. Automation generation (`src/handlers/automation-generate.ts:87`), uncached explanation (`src/handlers/automation-explain.ts:64`) and ambiguous email triage (`src/ai/email-triage.ts:100`) likewise call paid models without `UsageService` reservation.

**Preconditions/impact:** a consented authenticated user/API key can vary transaction text or generation drafts to avoid caches and keep spending after the Free AI quota is exhausted. Email triage additionally exposes spending to a sender who knows an already verified, consented forwarding alias: triage precedes deduplication at `src/handlers/email-forwarding.ts:156` and `:173`, and sender-authentication checks occur later for posting. This does not imply forged email can pass the separate authenticated auto-post checks.

**Minimal remediation:** enforce one mandatory atomic reservation per billable operation, after a permitted cache hit and immediately before the first external call; include all legacy/generation/triage paths. Deduplicate intake before paid triage and apply per-alias ingress limits. Keep consent, reservation and telemetry separate. Add exhaustion/concurrency tests proving zero provider calls and zero financial writes on denial. Input character/byte limits are also needed on legacy text/generation handlers (`transaction.ts:40`, `parse.ts:32`, `automation-generate.ts:36`); output limits alone do not bound input cost.

Actual deployed versions, optimizer platform, CDN/WAF mitigations and live endpoint exposure were not queried.

### A05 — High, confirmed native design defect: implicit OAuth tokens return through an unclaimed scheme

**Evidence:** mobile `src/stores/auth-store.ts:218` uses `expense-tracker` for Google OAuth and lines 233–244 extract `access_token`/`refresh_token` from the callback URL. Mobile `src/lib/supabase.ts:41` configures no PKCE flow; installed Supabase defaults to `implicit` (`node_modules/@supabase/supabase-js/src/lib/constants.ts:32`). Android `android/app/src/main/AndroidManifest.xml:25` registers custom scheme filters without a verified HTTPS app link; iOS configuration similarly declares the custom scheme (`app.json:9`). Recovery also accepts bearer credentials via that scheme (`src/lib/auth/recovery-link.ts:31`).

**Preconditions/impact:** a malicious co-installed app able to register/intercept that scheme, especially on Android, can obtain returned bearer/refresh tokens during a login/recovery attempt. No device interception experiment was performed; `openAuthSessionAsync` behavior and provider redirect allowlists require device/configuration review. Verifying a stolen token with `getUser` does not bind it to the initiating device.

**Minimal remediation:** use authorization code + PKCE, keep the verifier in protected app storage, and exchange the callback code rather than accepting reusable tokens in links; adopt verified app/universal links when available. Preserve exact callback validation and recovery intent validation. See [RFC 8252 §8.1](https://www.rfc-editor.org/rfc/rfc8252#section-8.1) and [Supabase PKCE flow](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

### A06 — High release blocker, confirmed configuration: Android release uses the tracked debug key

**Evidence:** mobile `android/app/build.gradle:100` defines standard debug signing and `:112` selects `signingConfigs.debug` for release at line 115. `android/app/debug.keystore` is tracked. No key material was inspected or printed.

**Preconditions/impact:** an APK distributed from that release configuration is signed with the shared development key. An attacker possessing the same key and convincing a user to install a replacement can impersonate a signed update and access the application's existing sandbox. The repository configuration does not prove any distributed artifact used it; EAS/Play signing may replace it.

**Minimal remediation:** fail release builds without an explicitly configured private release/upload signing identity, keep it outside git, and verify the final artifact certificate before distribution. Use [Android release signing guidance](https://developer.android.com/studio/publish/app-signing). Do not rotate an existing production identity without first establishing what certificate was actually shipped.

### A07 — High financial-integrity risk, legacy compatibility retained: direct owner table writes can bypass reviewed commands

**Evidence:** `supabase/migrations/20241125000008_add_multi_user.sql:58` creates authenticated `FOR ALL` transaction RLS. `20260929000130_manual_transaction_atomic.sql:15` explicitly preserves the legacy authenticated insert/update grant for mobile while removing client quota-table writes at lines 19–21. `20260929000160_guard_account_delete.sql:4` revokes direct DELETE, but the reviewed migration set contains no corresponding general INSERT/financial UPDATE revocation. The backend still creates transactions and changes balances through separate service-role requests (`src/services/supabase/transactions.service.ts:12`, `:22`; `accounts.service.ts:112`).

**Preconditions/impact:** if the documented legacy grants/default Supabase grants are present in production, an authenticated owner can write ordinary transactions outside the reviewed creation/patch RPC, bypass transaction-count enforcement and leave balances inconsistent. Concurrent legacy service writes can also lose balance updates because `updateBalance` performs read/compute/PATCH. This is owner-data integrity and limit enforcement; it is **not** a demonstrated cross-owner disclosure. Actual deployed grants were not queried.

Existing transaction ownership/currency triggers still block foreign account references (`20261020000060_statement_currency_transfers.sql:13`); immutable reviewed-evidence guards protect additional sensitive paths. Those safeguards do not substitute for routing ordinary posting through one atomic command.

**Minimal remediation:** inventory released clients first, complete the native reviewed-command migration, then revoke direct INSERT and financial-column UPDATE from browser/native roles. Move the legacy service writer to an atomic owner-scoped RPC with idempotency, quota and balance changes. Add role-level tests for denied direct writes. Do not break a shipped legacy mobile client by revoking grants before a compatible rollout.

### A08 — Medium, confirmed configuration: Android backup includes an ordinary SQLite financial cache

**Evidence:** mobile `android/app/src/main/AndroidManifest.xml:16` sets `allowBackup="true"` without scoped backup/data-extraction rules in the reviewed main manifest. `src/database/index.ts:24` uses the ordinary WatermelonDB SQLite adapter, with no application-level database encryption configuration. Auth tokens use SecureStore (`src/lib/supabase.ts:16`), which protects a different data store.

**Preconditions/impact:** access to a permitted device/cloud backup or the app sandbox can expose cached financial records and local drafts independently of token storage. OS filesystem encryption and sandboxing still apply; no backup was extracted. Restored caches may also outlive their originating session, making the existing active-owner gate necessary.

**Minimal remediation:** exclude financial database/cache and draft files from Android cloud/device-transfer backup, document the policy, and evaluate database encryption against the physical-device threat model. Keep the separate native Shortcut vault's current backup exclusion/device-only key protection (`ios/ExpenseTracker/AnottoShortcuts/ShortcutVault.swift:117`, `ShortcutKeychain.swift:60`).

### A09 — Medium, confirmed missing defense: CSRF/origin checks and framing policy are inconsistent

**Evidence:** web financial chat (`app/api/financial-chat/route.ts:8`) and several reviewed routes explicitly require same-origin cookie requests. Web automation creation (`app/api/automation-rules/route.ts:42`) and document upload (`app/api/documents/route.ts:48`) do not. The automation handler accepts JSON without a content-type restriction. The installed SSR cookie defaults use `sameSite: 'lax'` and `httpOnly: false` (`node_modules/@supabase/ssr/src/utils/constants.ts:5`); JavaScript access is part of its client auth design. Web `next.config.ts:6` and landing `vercel.json:1` define no application-wide CSP/frame-ancestors policy.

**Preconditions/impact:** a compromised same-site sibling origin can send credentialed simple requests to unguarded cookie-authenticated mutation endpoints. Lax cookies mitigate many cross-site requests but do not establish exact-origin authorization. Framing/clickjacking and XSS impact depend on actual platform response headers and an attackable browser context; no such production condition was confirmed. No direct attacker-controlled HTML execution path was demonstrated: landing HTML sinks select bundled, allowlisted locales (`src/i18n.ts:14`), and reviewed web financial text is rendered through React.

**Minimal remediation:** consistently apply the existing exact-origin guard to unsafe cookie-authenticated methods, while keeping explicitly authenticated native bearer requests supported. Add a CSP beginning with `frame-ancestors 'none'`, appropriate `nosniff`/referrer policy and a staged script policy compatible with Next. Verify deployed platform headers before claiming they are absent. Do not attempt to force HttpOnly cookies without redesigning the browser Supabase session contract.

### A10 — Medium, confirmed source pattern: user rules execute unrestricted regular expressions on servers

**Evidence:** web `app/api/automation-rules/route.ts:72` inserts user-controlled conditions and `lib/api/server.ts:137` constructs/tests `description_regex` with JavaScript's backtracking engine. Backend `src/services/supabase/automation-rules.service.ts:186` does the same. No regex complexity or execution bound exists at these call sites.

**Preconditions/impact:** an authenticated user who can save a pathological rule and supply matching transaction text can consume Worker/server CPU until platform limits intervene. An attacker who can influence messages for an owner with an existing pathological rule has a second path. No expensive regex was executed during this audit.

**Minimal remediation:** limit pattern/input sizes and use an approved non-backtracking engine or restricted rule grammar. Syntax validation and a timeout around a synchronous `.test()` alone do not prevent event-loop blocking. Add a safe rejection test for nested ambiguous quantifiers.

### A11 — Medium, confirmed delivery gap: deploy workflow omits tests/audit and trusts mutable action tags

**Evidence:** backend `.github/workflows/deploy.yml:13` uses version tags for three actions, installs dependencies at line 28, runs lint/typecheck at lines 30–34, then provisions a provider secret and deploys at lines 36–49. It contains no test or advisory gate and no explicit minimal `permissions` block. Lockfiles are present; the install is frozen.

**Preconditions/impact:** a regression passing lint/typecheck can deploy without the security tests demonstrated below; a compromised action tag/dependency lifecycle script executes in a pipeline that later handles deployment secrets. This is pipeline exposure, not evidence of a current supply-chain compromise. Web/mobile/landing GitHub workflow gates were not present in their local trees; external Vercel/EAS/branch rules were not queried.

**Minimal remediation:** run relevant security/full tests before deployment, add reviewed advisory triage with production/reachability distinctions, pin actions to reviewed commit SHAs, set least-privilege workflow permissions, and restrict lifecycle scripts through the package-manager policy appropriate to the chosen pnpm version. Backend `.gitignore:1` ignores `.env.local`/`.dev.vars` but not general `.env`/credential patterns; extend it defensively. The current tracked-text credential scan found no candidates, so no blanket credential rotation is justified by this audit.

## Controls inspected without a demonstrated bypass

- **Owner/RPC boundaries:** `src/utils/auth.ts:41` verifies JWTs against Supabase; service-role reads must remain explicitly owner-filtered. `src/services/supabase/financial-chat.service.ts:40` uses fixed bounded owner queries, not model SQL. Current SQL examples include `set_document_review_status` owner locking/audit (`20261020000070_document_review_status.sql:32`) and correction owner/idempotency checks (`20261020000080_statement_funding_correction.sql:45`). Selected role/RPC tests passed; the complete migration chain and deployed grants were not exhaustively exercised.
- **Document provenance and financial posting:** uploads go to owner-prefixed private paths (`web/app/api/documents/route.ts:65`), previews recheck owner/path then issue five-minute signed URLs (`web/app/api/documents/[id]/inspect/route.ts:81`). Storage policies restrict owner folders (`20260929000010_document_inbox.sql:172`). Extraction produces drafts; dedicated reviewed SQL remains the financial authority. PDF parsing disables dynamic evaluation/XFA/fetch, uses page/text/memory limits, and terminates its isolated worker (`web/lib/pdf-text.ts:35`, `:92`, `:107`). Upload size checks occur after request materialization, so host streaming/request limits still matter.
- **Email authenticity:** initial forwarding confirmation detects envelope sender/subject (`src/handlers/email-forwarding.ts:142`), which is not proof of bank origin. Financial auto-post independently requires routing evidence with DKIM/DMARC/ARC pass, exact sender/subject, message fingerprint, bounded timestamps and unique routing evidence (`src/handlers/forwarded-email-scheduled.ts:119`, `:288`). No claim is made that forged visible headers establish authenticity. Paid triage abuse remains A03.
- **AI privacy/injection:** consent starts false and fails closed on lookup errors (`src/services/supabase/ai-consent.service.ts:36`); consent changes require an interactive session (`src/utils/auth.ts:34`). Text completions request ZDR/no collection and bounded recovery (`src/ai/openrouter.ts:97`, `:104`); image completions request no collection but do not promise universal ZDR (`src/ai/vision.ts:190`, landing `src/locales/legal-es.json:49`). Chat has fixed reads/corpus acknowledgement, bounded snapshot, source-ID checks and rejects model links (`src/handlers/financial-chat.ts:39`, `:69`; `src/utils/financial-chat-response.ts:13`). These controls limit impact; regex/prompt wording is not a proof against all multilingual/indirect prompt injection. No live adversarial model campaign was run.
- **Native ownership/storage:** the current uncommitted native cache-owner gate denies a different/unverified owner (`src/database/cache-owner.ts:38`); owner requests recheck session after response (`src/lib/api/owner-request.ts:9`, `:21`). The Shortcut vault uses AES-GCM, bounded queue/storage and device-only Keychain keys (`ios/ExpenseTracker/AnottoShortcuts/ShortcutVault.swift:137`, `ShortcutKeychain.swift:64`). iOS ATS disallows arbitrary loads (`ios/ExpenseTracker/Info.plist:49`); Android cleartext opt-in was found only in debug manifests. Final merged release manifests were not built/inspected.
- **Secrets:** a redacted pattern scan of tracked source/config/docs found no private-key/provider-token/Telegram-token/JWT candidates in backend/web/mobile, and later landing. Only filenames/line numbers would have been retained for candidates; values were never output. Untracked `.env` files, personal exports, history, provider dashboards, CI secret scopes and native signing material were deliberately not read. A clean scan does not establish no historical leaks.
