# Financial command compatibility inventory — 12 November 2026

## Result and scope

**A07 remains open.** Current web and uncommitted native transaction paths largely use reviewed commands, but legacy Worker posting still inserts transactions and updates balances in separate service-role requests. A grant revocation alone would neither fix that service-role path nor prove compatibility with distributed offline clients. The concrete next implementation should replace that legacy writer with an owner-scoped atomic, idempotent server command; client privilege cutover follows separately.

This was a read-only code/build-metadata inventory. No grants were queried or revoked, no database mutation or financial record access occurred, and no source/release files were changed. It follows [the staged security gates](../plans/2026-11-12-security-next-gates.md) and [security follow-up](2026-11-12-security-followup.md). Paths labeled web/mobile refer to sibling `spends-assistant-web` and `spends-assistant-mobile` repositories.

## Offline/retry behavior inspected

The current native command queue verifies the active owner before transport and before recording acknowledgement (`mobile/src/database/transaction-command-sync.ts:39`, `:99`). It persists pending/failed/acknowledged command state and frozen payloads, reuses prior commands for uncertain outcomes, and adopts canonical server identities after Watermelon push acknowledgement (`:131`). The sync layer routes transaction changes through this queue, while committing account/category prerequisites first (`src/database/sync.ts:424`). This is useful local compatibility evidence, not proof that every old dirty row, device restore or shipped app version uses the same code.

Relevant existing tests are `mobile/tests/database/transaction-command-sync.test.ts`, `tests/lib/api/financial-transactions.test.ts`, `tests/utils/transaction-command.test.ts`, and native sync suites. Backend atomic/manual/reviewed command tests and web route tests provide additional fixtures. These tests were inventoried, not rerun during this read-only task while other agents built release artifacts.

The legacy Worker transaction handler performs pre-write duplicate reads (`src/handlers/transaction.ts:191`); these are not a durable atomic idempotency claim. Email/Telegram alternate posting branches must also migrate. A hash of free-form text is not automatically a unique financial event: genuine repeated payments can share text. Do not silently invent event identity from that hash.

## Privilege and server-command constraints

The original compatibility migration explicitly retains legacy transaction writes (`supabase/migrations/20260929000130_manual_transaction_atomic.sql:15`), while a later migration revokes direct DELETE (`20260929000160_guard_account_delete.sql:4`). Owner RLS is present in the migration set (`20241125000008_add_multi_user.sql`), but owner RLS is not quota/idempotency/balance command enforcement. Current deployed grants and the complete production migration chain were not queried in this task; source history does not prove live privileges.

Importantly, the current manual command derives its owner from `auth.uid()` and grants execution to `authenticated`, explicitly revoking service_role (`supabase/migrations/20261019000080_manual_currency_posting.sql:237`). The Worker currently uses service credentials and also accepts per-user API keys. Merely replacing its table POST with a call to the existing manual RPC is therefore not a valid migration: the owner/authentication and grants contract would be wrong.

## Concrete next changes and cutover gates

1. **Replace the Worker legacy writer first, without revoking client grants.** Design a service-only server wrapper with explicit verified owner and stable request/event identity, backed by the same audited transactional invariants as reviewed posting. Keep client `auth.uid()` and service-owner wrappers distinct, with a nonpublic common core if factored. Validate account/category ownership, currency, quota, duplicate/replacement restrictions and all balance changes in one transaction. Give `/transaction`, legacy email and bound Telegram adapters stable retry keys appropriate to their authenticated source. Preserve capture/review semantics rather than introducing new automatic posting paths.
2. **Test the atomic boundary before rollout.** Focused failing tests must show no partial transaction/balance/quota changes on failure; exactly-once replay after uncertain transport; conflict on changed payload under one key; concurrent quota/balance safety; wrong-owner account/category denial; and service-only/client-only grant separation. Use real multi-session PostgreSQL for interleavings. Exercise both alternate posting branches in each legacy handler. Reuse deterministic synthetic fixtures without querying personal records.
3. **Remove remaining web direct transaction UPDATE dependence deliberately.** Migrate bulk metadata updates to an owner/review-aware bulk command, or establish a narrowly scoped privilege contract only after its category/review triggers are verified. Do not revoke UPDATE globally while this route still requires it.
4. **Prove the native rollout boundary.** Complete the isolated candidate evidence, run command/offline retry tests, and inventory actual distributed versions and pending-queue upgrade behavior. Require successful create/edit/delete/transfer/reversal and network-retry behavior against the released web contract. Record unsupported-client handling without discarding queued work. Local source presence or simulator success cannot replace this inventory.
5. **Then inspect live grants and stage revocation.** With compatibility established, verify metadata-only deployed grants/RLS/RPC definitions, rehearse the complete migration and rollback, verify the required private backup, and remove only the identified direct INSERT/financial UPDATE bypasses. Confirm role-level denied direct writes and permitted commands after cutover. Do not change unrelated native table grants, assume service_role is constrained by client revocation, or mark A07 resolved before deployment evidence exists.

These are technical readiness gates within the existing authorized work, not additional approval requests. No privilege cutover or distributed-client compatibility claim is made by this report.
