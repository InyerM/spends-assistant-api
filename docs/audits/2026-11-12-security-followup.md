## Immediate priorities

1. **A03 remains high: enforce paid-call reservations across every legacy entry point.** `src/parsers/expense.ts:97` still treats `beforeExternalCall` as optional; `src/handlers/transaction.ts:87`, `email.ts:100`, and `telegram.ts:215` omit it. Generation (`automation-generate.ts:87`) and uncached explanation (`automation-explain.ts:64`) track usage without quota reservation. `src/ai/email-triage.ts:100` makes a paid request before email fingerprint/deduplication (`src/handlers/email-forwarding.ts:178`). Consent and best-effort usage telemetry do not enforce a budget. A consented user can vary cache keys; an external sender with a verified forwarding alias can repeatedly trigger eligible triage. Recommended implementation: one shared atomic reservation boundary immediately before a cache-miss provider call, retain cache hits without charging, deduplicate before triage, and bound legacy inputs. Focused denial/concurrency tests must assert zero provider calls and zero financial writes; avoid changing posting as part of the budget patch.
2. **A04 remains high priority: upgrade web Next and native image dependencies together.** Web `package.json:40` still pins Next `16.1.6`, line 49 Sharp `0.34.5`, and line 70 its matching ESLint config. The fresh registry response still matches four critical Next advisories. The minimum Next version covering the returned ranges is `16.4.1`; Sharp needs `>=0.35.5`. Upgrade on an isolated branch with Linux build, auth/localization/document tests, actual dependency resolution and compiled OCR worker smoke. Do not use a transitive override as a substitute for checking framework compatibility.
3. **New production dependency follow-up: postal-mime `4.0.2` remains affected by header CPU amplification.** Backend lockfile resolves `postal-mime@4.0.2` (`pnpm-lock.yaml:1455`); raw external mail reaches `PostalMime.parse` (`src/utils/email-mime.ts:92`) after destination lookup and byte bounds (`src/handlers/email-forwarding.ts:108`). The [maintainer advisory](https://github.com/postalsys/postal-mime/security/advisories/GHSA-f2hq-32vh-53cc) fixes quadratic joined encoded-word decoding in `4.0.8`. Existing `maxHeadersSize: 16 KiB`, nesting limits (`email-mime.ts:93`) and ingress byte limits materially reduce exposure; the advisory explicitly recommends lower header limits as a workaround. Therefore this is an affected reachable parser with mitigation, not a demonstrated service-wide denial. A same-major lockfile update to `>=4.0.8` plus current MIME/PDF intake tests is a bounded early task; do not execute an expensive adversarial payload on shared services.

## OCR changes to A04 reachability

The October report's image analysis predates direct image canonicalization. The released OCR flow now downloads an owned storage object and passes it to `prepareImageForOcr` (`web/app/api/documents/[id]/extract/route.ts:83`); `web/lib/pdf-ocr.ts:35` invokes Sharp and reads metadata before checking the resulting format. The upload validator allows only PNG/JPEG/WebP byte signatures (`web/lib/documents.ts:5`), image size is bounded, pixel limits are configured, and processing occurs in a terminable worker. These are meaningful controls, but worker threads are not a separate OS security boundary for native memory corruption.

The [Sharp maintainer advisory](https://github.com/lovell/sharp/security/advisories/GHSA-wq5f-xc86-pv6w) identifies a librsvg memory defect with conditional glibc-Linux RCE and recommends Sharp `0.35.5` or disabling `VipsForeignLoadSvg`. No SVG/AVIF bypass of upload signatures, hostile stored object, vulnerable native-platform condition, or exploit was demonstrated. Unlike October, an application Sharp execution path is now confirmed; upgrade urgency increases without treating all critical optimizer advisory preconditions as satisfied. Consider explicit decoder blocking/allowlisting as defense in depth, with regression tests for unsupported bytes before native decoding.

## Authorized local A03 quota remediation

The coordinator approved the bounded shared-guard plan before implementation. `src/utils/ai-parse-quota.ts:18` uses the existing atomic `UsageService.incrementAiParses` RPC and converts quota exhaustion to `429 PARSE_LIMIT_REACHED`, and unavailable reservation to a sanitized `503 AI_QUOTA_UNAVAILABLE`. No SQL, input-limit change, new provider retry, or financial posting change was added.

The parser now requires a reservation hook immediately after owner consent and before a cache-miss provider request (`src/parsers/expense.ts:98`). Its deterministic incoming-review branch and cache hits return before consent/reservation. All four current callers supply the shared reservation: parse (`src/handlers/parse.ts:77`), transaction (`transaction.ts:93`), legacy email (`email.ts:106`) and Telegram (`telegram.ts:225`). Telegram returns a fixed friendly quota/unavailable message without echoing expense text. Legacy HTTP handlers return the typed quota response before their normal failure logging/posting paths.

Automation generation reserves inside the consent-checked tracked callback (`src/handlers/automation-generate.ts:92`). Explanation reserves inside its existing single pending-generation promise (`automation-explain.ts:69`): cache hits cost no reservation and concurrent identical generation requests share one. Ambiguous forwarded-email triage reserves only inside the actual provider callback (`src/ai/email-triage.ts:106`); missing/denied/unavailable reservation falls back to pending review without a provider call. Deterministic email classification, PDF intake and disabled-AI branches remain quota-free. Inbox analysis, OCR, chat, vision and statement extraction retain their own existing reservation boundaries; no global telemetry charging was introduced.

Validation: the missing parser hook and shared-helper regressions were observed failing before implementation (`quota-red.log`). The final focused **180 tests in 11 files** passed, covering denied/unavailable quota with zero provider work, legacy-handler denial before financial mutations, friendly Telegram replies, cache/deterministic bypass and concurrent explanation single charging (`quota-focused-final.log`). An initial expanded run had three test assertions that incorrectly treated permitted owner-history GETs as writes; those were corrected to distinguish POST/PATCH/DELETE, without application changes. The existing reservation/atomic SQL suites passed **74 tests in seven files** (`quota-existing-reserved-tests.log`); a subsequent OCR success assertion verifies exactly one AI-parse reservation and its 11-test file passed (`quota-ocr-single-reservation.log`). Backend TypeScript, scoped source lint, formatting and whitespace checks passed. Full coordinated suite and independent review remain the coordinator's gates.

**Still open:** forwarding deduplication occurs after triage, so duplicate deliveries can consume separate available reservations; this patch caps them but does not supply an atomic pre-triage claim or per-alias ingress limiter. Legacy input byte/character bounds remain separate follow-up. Failed paid requests retain their existing reservation behavior. These local source fixes are not deployment evidence and do not close all of A03's original abuse-hardening scope.
