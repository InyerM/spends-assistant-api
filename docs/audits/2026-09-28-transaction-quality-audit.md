# Transaction quality audit — 2026-09-28

## Scope and reproducibility

The read-only script [`scripts/transaction-audit.mjs`](../../scripts/transaction-audit.mjs) paged the `transactions` endpoint, identified the single profile with **1,516 active rows**, and fetched all its active transactions, accounts, and categories. It rejected a non-unique count or a changed transaction count. The other profile's 23 active transactions were used only in the initial count check; they were not audited. No database mutation, external model call, or customer content was made by this audit. Run locally with `node scripts/transaction-audit.mjs --expected-count=1516`; its output contains aggregate counts only. The service key comes from the backend `.env.local` at runtime, and the public project URL comes from the web `.env.local`. Do not redirect output to a tracked file without reviewing it.

This report contains no customer names, descriptions, user or account identifiers, transaction IDs, raw text, or balances. The audit's in-memory calculations do inspect these fields. Heuristic counts below are review signals, not verified classification errors or confirmed duplicate payments.

## Duplicate, transfer, and recurrence review

The script compares pairs with the same date, account, and amount. It found **16 possible pairs** with no additional strong signal and **11 stronger pairs**. All 11 stronger pairs share normalized raw text; the strong rule can also use description, time, and source. Pairs are counts, not distinct rows or confirmed duplicates. Different transactions can share these features, and events on adjacent dates or different accounts are outside this candidate rule. Existing confirmed and pending statuses may overlap the candidates.

There are 27 transfer rows without a destination account; this may represent transfers to external accounts. A word-pattern check found 254 expense rows with transfer-like wording, 90 rows with a Nequi mention in description, notes, or raw text, and 43 of those 90 recorded as expenses. These sets overlap. One Nequi group covering four rows has the same normalized description, amount, and type with at least two intervals of 25–35 days. This is a recurrence candidate, not evidence that those rows are the same merchant, subscription, or duplicate transaction. Grouping by counterparty requires private review because the current fields do not reliably separate recipient from bank boilerplate.

Keyword checks found one investment-like expense, one loan-like income, and 67 loan-like expenses. These counts may include ordinary purchases or installment interest. They cannot establish whether a contribution should be a transfer, whether a disbursement is income, or how principal, interest, and fees should be split. Review against statements and account ownership before changing type or category.

## Account and balance evidence

All 1,516 rows reference an account in the selected profile, with no inactive account references and no transfer whose source and destination are the same account. The script computes signed net movement per account in memory. **No opening balance or complete reconciled statement interval is available in this audit**, so it cannot soundly compare those movements to the ten reported balances. The script omits all balance amounts from output. Zero reconciled rows corroborate that there is no recorded completed transaction reconciliation in this profile; they do not prove the stored balances are wrong.

## Prompt and workflow gaps

At audit time, the parser prompt in [`src/constants/parse-expens-system-prompt.ts`](../../src/constants/parse-expens-system-prompt.ts) embedded a fixed category list, while categories are user-owned in the schema. It also had a malformed `Source` rule, mapped all Nequi input to `transfer` payment type, and instructed choosing a specific category even where evidence was weak. This branch subsequently corrected those three prompt instructions and added synthetic prompt-contract tests; it did not measure model output quality. The fixed category catalog remains a separate issue. These are code-level risks rather than measured causal explanations for the rows above. Evaluate prompt changes on an anonymized, labeled set containing Nequi transfers, recurring recipients, ordinary expenses, informational messages, imports, and loan/investment examples. Compare amount/date/account accuracy, non-transaction detection, category fit, and false duplicate rate before deployment.

## Proposed review order and limits

1. Review the 14 already pending duplicate statuses and the 27 candidate pairs with private transaction context. Treat identical raw text as stronger evidence, never automatic deletion.
2. Build reversible category and description proposals for the 292 uncategorized and 31 empty-description rows, prioritizing `sms-shortcut` and `csv_import`. Preserve before/after values and reviewer decision history outside this aggregate report.
3. Reconcile the 480 CSV rows lacking `import_id` with import history before using that history as a complete source of truth.
4. Review Nequi recurrence and transfer-like expense signals alongside statements and linked accounts; validate investment and loan treatment with statements before reclassification.
5. Establish opening balances and a statement interval before assessing calculated versus reported balances.

The exact reviewed rows may change after new imports or edits. This is a point-in-time audit of active rows only; 571 soft-deleted rows were excluded per the restart design. The private context needed to turn signals into transaction-level proposals was not copied to Git or exported by this audit.
