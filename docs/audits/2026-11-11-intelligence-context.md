# Intelligence context audit — 2026-11-11

Current local status: authoritative contact-linked history, bounded notes retrieval, and deterministic per-field rule precedence are implemented but not published. The implemented increments, compatibility changes and verification are recorded below; the original static findings are retained as historical context. Complete prompt restrictions are also preserved by `buildAutomationRulesPromptSection`, including raw text, exact amounts, account/category conditions and AND between condition groups. Unsupported or impossible conditions are omitted as whole rules, never partially broadened. Regression evidence is in `tests/services/transfer-processor.test.ts`.

The original static audit below concluded that improvements should preserve and reconcile authoritative context across routes before changing the intelligence model. The code already supplies rules and owner history to normal parsing and inbox analysis. At the original audit snapshot, the largest confirmed gap was that the web server retrieved contact-linked evidence, sent it to the worker, and the worker intentionally replaced client-supplied history with a different lexical lookup. The bounded fix addresses that gap without trusting the client payload. Another confirmed gap is inconsistent rule conflict resolution. The original review proposed contracts and a web-first increment without code changes; the separately documented implementation below changes the bounded context lookup and web identity forwarding only, with no database migration, model switch or deployment.

## Confirmed findings

### 1. Contact evidence is retrieved but replaced before model inference

Web `app/api/transactions/[id]/analyze/route.ts:42` calls owner-scoped `counterparty_category_followup`; lines 60–65 map its evidence into the worker request. The contact follow-up explanation route similarly sends evidence at `app/api/transactions/[id]/category-followup/explain/route.ts:39`. The worker fetches history from `input.description` and `input.type` at `src/handlers/category-review.ts:56` and then calls `reviewCategory({...input,history},...)` at line 108, replacing the supplied evidence. This is intentional defense against arbitrary client history, explicitly covered by `tests/category-review-handler.test.ts:94`; it should not be “fixed” by blindly accepting request history.

The authoritative contact SQL already loads same-contact/type descriptions and notes, including owner or shared category labels, bounded to eight evidence rows: `supabase/migrations/20261019000120_counterparty_review_context.sql:10`, `:16`. The worker replacement instead finds at most twelve lexical description matches and restricts the joined category to `category.user_id=owner`: `src/services/supabase/category-review-context.service.ts:44`, `:54`, `:57`, `:59`.

**Illustrative consequence, not a live incident:** a reviewed transfer to a saved contact named DEMO LINA has description “Transfer X9”; prior contact-linked movements have descriptions “School support” and notes “Monthly tuition.” Contact SQL can identify those rows, while a lexical lookup on “Transfer X9” cannot match them and may return none. A stronger model cannot recover evidence it never receives. Shared-category history also satisfies the contact SQL but is excluded by this worker category join.

Recommendation: resolve context authoritatively on the server from an owned transaction/contact identity, then combine contact-linked and lexical evidence with provenance and deduplication. Keep rejecting unverified arbitrary history payloads. Contact identity should come from owned links, not same-name guessing. The audit establishes evidence loss, not that any resulting category is wrong.

### 2. Rule priority and chaining have conflicting semantics

`src/utils/inbox-analysis-proposal.ts:22` sorts high priority first, then lines 55–104 apply every matching rule to evolving state; lines 86–87 let later category writes overwrite earlier ones. The legacy worker service loads `priority.desc` (`src/services/supabase/automation-rules.service.ts:60`) and applies all matching rules sequentially (`:128`, `:144`). Category review instead uses the first eligible category rule (`src/handlers/category-review.ts:64`) and forces its category when posting kind matches (`src/ai/category-review.ts:98`). Account detection declines differing-account ambiguity regardless of priority; this is explicitly tested at `tests/services/supabase/automation-rules.service.test.ts:49`.

**Deterministic counterexample:** two matching expense rules set category A at priority 100 and category B at priority 10. Inbox and sequential post-parse application finish with B; category review chooses A. This follows source execution order, not an observed production test. Existing inbox tests establish that rule B can intentionally depend on account state written by rule A (`tests/utils/inbox-analysis-proposal.test.ts:36`), so simply stopping after the first match would break supported chaining. Those tests do not establish how two rules writing the _same field_ should resolve.

Recommendation before implementation: define higher-priority first ownership of each scalar field, preserve explicit dependency/chaining stages, accumulate notes predictably, and expose conflicting assignments rather than silently choose a lower-priority one. Add a stable tie-break for equal priority. This is a proposed contract, not a discovered existing promise. Verify web rule engine parity and migration consequences before changing financial posting behavior. Keep the current behavior unchanged in this report-only pass.

### 3. Lexical retrieval ignores current notes and contact identity

`CategoryReviewContextService.history` extracts up to six words from description only and searches historical **description** only, while returning notes for rows already found (`src/services/supabase/category-review-context.service.ts:44`, `:57`, `:68`). Current notes are passed to the review model (`src/ai/category-review.ts:55` spreads input) but do not influence which rows are retrieved. The generic parser looks up history using raw input, so notification boilerplate can occupy the six-token budget; inbox analysis improves this by preferring extracted merchant (`src/services/inbox-analysis.ts:62`).

**Illustrative gap:** current description “DEMO SHOP,” notes “replacement laptop for work,” prior description “Equipment purchase,” notes “DEMO SHOP laptop.” The retrieval does not search notes, so relevant prior context can be absent despite both notes fields being useful. Searching all notes indiscriminately would increase irrelevant or private context; use bounded owner-scoped retrieval and measured recall rather than an unlimited prompt.

The frontend also has a separate description-token frequency heuristic (`spends-assistant-web/lib/document-review.ts:184`) requiring at least two matches and a greater-than-two-times lead; its forwarded category helper hardcodes selected grocery merchants before history (`lib/shortcut-inbox/create-draft.ts:209`, `:216`). This is another proposal path with different inputs, not proof the final review overrides user rules. Consolidate provenance and precedence rather than allow silent disagreement.

### 4. The parser's rule prompt is a lossy representation of the executable rule

`buildAutomationRulesPromptSection` filters eligible actions and emits description contains/regex, amount range and source, plus type/category writes (`src/services/transfer-processor.ts:208`, `:223`, `:239`). It omits supported raw-text, exact-amount, from/to-account and category conditions used by the executable matcher (`src/services/supabase/automation-rules.service.ts:196`, `:219`, `:225`, `:231`, `:235`). It can omit an entire rule when none of its supported textual conditions is emitted (`src/services/transfer-processor.ts:243`).

**Illustrative gap:** a rule requiring description “DEMO STORE” **and** source account A can be rendered to the parser with the description condition but no account constraint. It may influence parsing for account B; deterministic post-processing may later correct a write path, but the parse-only proposal can still disagree. This is a static capability mismatch; the audit did not run an LLM to reproduce the result. Prefer one evaluated-rule result/context contract over asking the model to re-execute a partial serialized rule.

### 5. Description and notes policies differ by route

The generic expense parser permits notes only when they are a bounded contiguous normalized source substring, excluding secret-like strings and digit runs (`src/parsers/expense.ts:19`). Forwarded email suggestions bound and normalize description/notes through `safeCopy`, but do not apply the same substring support check (`src/ai/forwarded-email-suggestion.ts:26`, `:162`). Category review asks the model to preserve meaningful original notes, then accepts any returned notes string up to 1,500 characters (`src/ai/category-review.ts:31`, `:135`). Rules append notes independently (`src/utils/inbox-analysis-proposal.ts:96`).

**Illustrative inconsistency:** a user source note “annual health visit” can be paraphrased by one suggestion route, while the same paraphrase is removed by the parser because it is not a substring. A model-generated “annual health visit” may be accepted by the review route even without source support; this is an allowed output shape, not evidence that hallucination occurred. Keep source/user notes immutable as evidence and return proposed notes separately with provenance and an explicit user-visible change. Separate a short merchant/purpose title from extra source context; never infer purchase purpose merely from a person or bank name.

## Implemented increment: authoritative contact evidence

After this audit, the first bounded context improvement was implemented locally. `CategoryReviewContextService.reviewHistory` validates the supplied current transaction against both ID and authenticated owner before retrieving context (`src/services/supabase/category-review-context.service.ts:15`). A missing, foreign or deleted source produces a 404 before quota or model inference (`src/handlers/category-review.ts`, `ReviewTransactionNotFoundError` branch). The lookup derives contact identity from the owned transaction link and owned counterparty, using the named composite foreign keys declared by the existing schema. No name matching or caller-supplied contact identity is introduced.

The service loads at most eight same-contact/type, nondeleted categorized movements, allowing active owner or shared categories and excluding foreign categories. It excludes the current transaction, orders by date and ID descending, and merges contact-first with lexical evidence up to twelve unique rows. Existing lexical retrieval and category-choice catalog behavior are retained; extending notes-based search or selectable shared categories remains outside this increment. Editable current description and notes still reach the model, while arbitrary client history remains ignored. Rule priority/chaining and financial SQL paths are unchanged.

The web follow-up explanation route now sends the selected row's transaction identity, including the selected target when applicable; the existing transaction analysis route already supplies it. Mobile uses the common endpoint, so no separate mobile prompt or implementation was added. Source/target identity and foreign target rejection are covered in `spends-assistant-web/tests/app/api/category-followup/explain.test.ts`; backend owner rejection, ignored forged history, current exclusion, contact evidence, lexical fallback, deduplication and bounds are covered in `tests/category-review-context.test.ts` and `tests/category-review-handler.test.ts`.

Actual HTTP integration against ephemeral local PostgreSQL 16 and PostgREST 16.5 validated the named composite embeds and nested `category.or` filter: [sanitized result](2026-11-11-contact-context-integration.json), [synthetic schema and rows](fixtures/2026-11-11-contact-context.sql). The service returned only `contact-old` and `shared-old`, excluded current/deleted/wrong-type/foreign-category rows, and rejected a foreign source. The standalone server used a synthetic JWT and the same service request queries with the Supabase `/rest/v1` proxy prefix removed. This tests query semantics against a minimal schema, not every production migration or deployed schema. Both created containers and their isolated network were removed afterward. No user data, production database or real model call was involved.

## Implemented increment: bounded notes retrieval

Category review now forwards editable current notes to authoritative history retrieval. The lexical query searches both historical descriptions and notes using at most six unique tokens, reserving the first three meaningful current-note tokens before filling from description and remaining notes. Token extraction scans at most 1,500 characters per field, strips ordinary edge punctuation, then accepts only complete Unicode-letter chunks of 3–40 characters and excludes common English/Spanish notification and credential labels. Internal query syntax, wildcards, email-like chunks and digit-bearing tokens remain excluded. A regression verifies ordinary `«Colegio», libros.` text remains searchable while `notes.ilike.*private*` cannot supply operators. Empty or boilerplate-only context does not trigger a lexical query.

The existing owner, posting type, nondeleted transaction and active/nondeleted owner-category filters remain mandatory for lexical history. The reviewed transaction is excluded in SQL and defensively from returned rows; lexical evidence is capped at twelve rows and ordered by date then ID descending. Verified contact evidence still takes precedence in the merged twelve-row budget, with at most eight contact rows; shared catalog categories remain eligible only in that existing contact retrieval path. No contact-name inference, client-history trust, financial posting, model change or deployment was introduced.

This is bounded substring retrieval, not semantic relevance ranking. Notes help candidate recall but do not decide a category or override description: conflicting purposes still require review. Strict token syntax intentionally misses internally punctuated/hyphenated terms and numbers; the stopword list is finite and not a general secret detector. Retrieved historical notes retain their existing 1,500-character bound and are owner-scoped evidence, not redacted summaries. The generic history helper also searches historical notes when called without separate current notes; its existing callers retain the same signature and owner filters.

Verification: the new notes-only regression and conflict/budget/injection-like input tests failed before implementation, then the context and handler suites passed together (14 tests). TypeScript `tsc --noEmit` and ESLint on the four touched TypeScript files passed on 2026-11-11. The environment had no `pnpm` executable, so verification used the installed package CLI entrypoints directly through Node. These new lexical-query tests mock HTTP; the earlier contact integration above validates owner/category query semantics against synthetic PostgreSQL/PostgREST, but the extended notes OR query has not separately been exercised against a running database.

## Implemented increment: ordered rule field precedence (pending release)

Backend post-parse rule application, inbox proposals and web post-parse application now evaluate rules by descending priority and ascending rule ID on ties. The first supported write claims each scalar action independently (`set_type`, `set_category`, `set_account`, `link_to_account`); an explicit null category is a real clear and claims the category field. Conditions continue to inspect the evolving transaction, allowing an earlier account action to unlock a later category action. Notes still append in evaluation order. Applied-action metadata in the post-parse services contains accepted actions rather than lower-priority suppressed scalar writes. Backend retrieval orders equal-priority rules by ID too, keeping category review's first eligible rule deterministic. Ambiguous account-detection matches continue to abstain.

Inbox ownership/catalog checks happen before claiming account or category fields, so an invalid high-priority foreign target does not block a valid lower target. A linked transfer claims its implicit transfer type and category clear together; it cannot override a higher explicit nontransfer type or higher nonempty category. Later type changes cannot erase that transfer, later source-account actions cannot create a self-transfer, and a transfer without an owned distinct destination becomes unresolved review metadata. The existing inbox regression that formerly expected a lower destination-conditioned rule to overwrite a prior transfer as income now expects the higher transfer to remain; the intermediate destination-conditioned note still appends. This intentionally changes conflicting-field precedence while preserving different-field chaining.

The web forwarded-review helper now exposes a matched category decision separately from its nullable category value. Its existing string/null wrapper remains compatible. The single analyze route consumes this decision so an explicit rule clear suppresses cached categories, recipient-history fallback and fresh AI category fallback. Rule IDs are retrieved for stable tie-breaking; cached and fresh review tests cover the clear. It remains a category-only helper, not a complete executable-rule engine: category/destination-dependent rules are still ineligible there.

Compatibility impact: existing overlapping rules that relied on later lower-priority scalar overwrites will produce different proposals after release. Equal-priority conflicts now resolve by rule ID rather than incidental database/input order. Review conflicting rules before deployment; this increment has not been deployed and does not migrate stored rules or financial records. Post-parse backend/web services retain their existing downstream target validation boundary and do not fetch new ownership catalogs; inbox target checks remain explicit. No SQL authority or financial confirmation boundary changed.
