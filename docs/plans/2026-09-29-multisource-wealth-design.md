# Multisource notification review and investment evidence design

Status: review draft. The current local web implementation is not deployed. This design uses the three privately supplied screenshots as observations, but does not copy their personal references or account details into Git.

## Notification backfill

Historical notifications arrive through SMS (Bancolombia, Nequi) and email (Lulo Bank credit card). The existing Worker `/transaction` and `/email` routes can write financial rows and are inappropriate for unattended replay. The existing private Shortcut inbox can accept provider-specific `source` values and preserves original text, receipt time, and a stable external ID. Use it as the first bounded intake for both channels, then present it in web as a **notification review inbox** rather than implying every item is a Shortcut. Preserve email sender, subject, and plain body in the review text; keep the actual email Message-ID as the external ID when available. Do not infer an email transaction time from the email receipt time.

The review step should group cross-channel evidence by explicit amount, transaction date, and independently verified account/card suffix. Matching raw text within one source is a strong replay signal. Equal amounts and close times alone are candidates, never automatic duplicates. The supplied Gmail print contains two separate messages in one thread, including a zero-amount notice; export individual Gmail messages and leave zero-amount notices out of financial creation. A Lulo credit-card purchase is an expense against its card account, while payment of that card is a transfer to the liability account; the existing Lulo loan is a different product with its own payment allocations. Require a dated statement balance before historic financial creation changes an account balance.

The local offline converter now accepts SMS exports and a bounded generic email JSON format. A Google Apps Script reads Lulo messages individually from Gmail and creates a private Drive JSON file for local conversion; it is not yet validated in the user's mailbox. Avoid the Bancolombia-only `/email` route for Lulo backfill. Keep the original source file private, count every item and per-item result, and preserve idempotency across retries. Evaluate a Lulo-specific parser against redacted purchase, zero-amount, refund, and card-payment examples before any proposed financial action.

## Investment products

Use separate position types within one investments area:

1. **Cash-denominated Pocket:** record reviewed contributions, pending withdrawals, settled withdrawals, and dated value snapshots. The supplied Tyba contribution screenshots show COP amounts and distinct initiation/finalization dates but no share quantity. Preserve both dates and require a reviewed effective date for the journal; a bank settlement may have another date. The withdrawal is still pending, so its final net amount and any remaining balance are not established. The current `investment_trades` schema requires a positive quantity for every buy/sell, so a Pocket event cannot be entered honestly from these screenshots alone. Add a cash-flow journal for this product or accept verified share quantities from a statement. Do not invent units or compute a return before final settlement and remaining balance are known.
2. **Quantity-denominated crypto:** record USDT buys/sells by exact asset quantity, COP consideration, fees, and chronological cost basis. The user identified the additional USDT as Earn yield; model that as a separate dated reward event, not as another P2P buy or an unexplained opening lot. The current position guard correctly prevents selling more units than recorded, so record the confirmed reward quantity and evidence before confirming the sell. Preserve the reward's valuation separately from the P2P rate and defer any cost-basis policy until supported by source records.

Both types need owner-scoped evidence links from the private image inbox to reviewed events, and one source screenshot may contain multiple orders. Extend specialized OCR drafts with provider, product, event kind, status, quantity/unit, COP amount, execution price, fees, and reference, retaining the original image and field-level source excerpt. The existing generic document observation only has one amount and lacks quantity and price. The UI should display extraction beside the source and require explicit confirmation. Neither OCR nor a journal event should implicitly create a bank transaction; a later reconciliation step links matched cash settlement legs without double counting.

## Verification

Use invented SMS, email, Pocket, and P2P fixtures to test date/amount parsing, different same-value payments, source replay, cross-channel suggestions, missing units, insufficient crypto quantity, and source-document ownership. Test the iPhone Shortcut export and mailbox export with small private samples before bulk intake. Apply the full Supabase migrations and multi-connection checks in staging before any production backfill. Mobile follows the approved web behavior.
